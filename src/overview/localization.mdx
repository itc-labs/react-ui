# Localization

The kit translates default control text: visible labels, loading and empty/error states, file validation, and accessible labels. Your application owns screen content, column and option names, backend errors, and business validation.

## Select a locale

Pass a locale code and a JSON-compatible catalog to `UIProvider`. Each catalog entry uses `UITranslation`; the array uses `UITranslations`. `UIMessages` describes the complete message dictionary.

```tsx
'use client';
import { Button, UIProvider, type UITranslations } from '@itclabs/react-ui';

const translations = [
  { locale: 'en-US', messages: { 'button.processing': 'Saving changes' } },
  { locale: 'vi-VN', messages: { 'button.processing': 'Đang lưu' } },
] satisfies UITranslations;

export function Example({ locale = 'en-US' }: { locale?: string }) {
  return (
    <UIProvider locale={locale} translations={translations} fallbackLocale="en-US">
      <Button loading>Save changes</Button>
    </UIProvider>
  );
}
```

The catalog can live in a JSON file. Add entries to support more languages; the provider selects messages by locale code. Keep date-library functions in `calendarLocales`, outside JSON. Use `messages` for local overrides.

Explicit component text props take priority over provider messages. For a string locale, catalog resolution merges the fallback dictionary/catalog and then the selected dictionary/catalog; English supplies remaining defaults. A locale created with `defineLocale` fills missing keys directly from English. The default locale is `viVN`; set `locale="en-US"` explicitly for English. Locale settings are independent of the icon theme and can change at runtime.

Do not change React keys or remount the UI when switching languages. The story preserves drafts, Select selections, row IDs, and Table pagination. Editor and file content is not translated automatically.

## Override messages

<Canvas of={Localization.MessageOverrides} />

`Button` accepts `loadingLabel`, `Spinner` accepts `label`, and `DialogContent` / `DrawerContent` accept `closeLabel`. Existing `label`, `placeholder`, `aria-label`, `error`, and `emptyState` props also take priority. Override other internal text with `messages`, using `UIMessageKey` autocomplete. Wrap a single control in a provider to limit an override to that subtree.

```tsx
import { Button, UIProvider } from '@itclabs/react-ui';

export function Example() {
  return (
    <UIProvider locale="en-US" messages={{ 'button.processing': 'Submitting' }}>
      <Button loading>Submit</Button>
    </UIProvider>
  );
}
```

Nested providers inherit message overrides while the selected locale remains the same; selecting a different locale clears inherited overrides before applying the new provider's messages.

## Custom locales and application i18n

Use `defineLocale` with a BCP 47 code and messages. Missing keys fall back to English. Dictionaries support templates such as `{count}` and `{name}`, plus plural forms such as `one`, `other`, and `few` selected with `Intl.PluralRules`. Plural messages require `other`. Interpolation returns strings and does not render HTML.

You can connect next-intl or i18next by passing translated messages to the provider. The kit does not prescribe an i18n library, router, or storage mechanism.

## Calendar locales in 0.4

Built-in `viVN` and `enUS` dictionaries no longer carry a date-fns locale. Date components resolve their date-library locale internally. To support another language or override calendar behavior, pass a `calendarLocales` map using locales from `react-day-picker/locale`:

```tsx
'use client';
import { DatePicker, UIProvider, type UITranslations } from '@itclabs/react-ui';
import { enGB } from 'react-day-picker/locale';

const translations = [{ locale: 'en-GB', messages: {} }] satisfies UITranslations;

export function Example() {
  return (
    <UIProvider
      locale="en-GB"
      translations={translations}
      calendarLocales={{ 'en-GB': enGB }}
    >
      <DatePicker label="Start date" />
    </UIProvider>
  );
}
```

Calendar resolution order is `calendarLocales[selected]` → `locale.calendarLocale` → built-in Vietnamese/English for the selected code → `calendarLocales[fallback]` → built-in Vietnamese/English for the fallback code → English. Locale map keys are canonicalized. `defineLocale` still accepts an optional `calendarLocale` for custom locale objects. Calendar headers and day labels use `Intl` with the selected locale code.

## Dates, numbers, validation, and SSR

`DatePicker` displays localized dates while its value and submitted hidden input remain `YYYY-MM-DD`. `TimePicker` keeps `HH:mm`; 12-hour mode translates AM/PM labels through the dictionary. Pagination, indexes, and IDs keep their underlying values; labels and summaries are formatted. Upload validation retains issue keys and parameters so visible errors can change language.

The locale provider adds no wrapper DOM and does not set `html.lang` or `dir`. Token configuration can add a style element; see [Theming](?path=/docs/guides-theming--docs). Set the document language in your application and use the same locale on server and client. Avoid choosing it from `navigator` during rendering, which can cause hydration mismatches.

Locale codes and catalog JSON can cross server boundaries. Configure date-library locales containing functions in a client module. Since 0.4, built-in dictionaries are message-only; they do not load date-library locale functions. The kit includes Vietnamese and English dictionaries; RTL layout support is not guaranteed.

Business schemas should return issue codes/parameters or use the application's current locale. Pass translated errors into fields: the kit does not translate arbitrary backend strings. Consumer-provided Toast and EmptyState titles and descriptions follow the same rule. See [Forms](?path=/docs/guides-forms--docs) and [Providers & adapters](?path=/docs/guides-providers-adapters--docs).
